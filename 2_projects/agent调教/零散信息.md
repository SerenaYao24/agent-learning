## 1. Agent 框架是指什么？

**Agent 框架（Agent Framework）**，本质上是一套**软件开发工具包（SDK）或底座架构**。

如果把大语言模型（LLM）比作**大脑**，Agent 框架就是**身体的神经系统和骨架**。单靠大脑（LLM）它是没办法自己去上网、读写文件、控制电脑的，它甚至记不住超过一定限制的聊天记录。Agent 框架的作用，就是把大脑包装起来，给它配上工具和记忆，让它变成一个能干活的“智能体”。

一个标准的 Agent 框架通常提供以下“组件”：

1. **Memory（记忆管理）：** 怎么帮大模型记住长期的用户设定和短期的对话上下文。
2. **Tools/Actions（工具集成）：** 怎么把 Python 代码执行器、谷歌搜索、文件读写 API 变成大模型能听懂、能调用的“手脚”。
3. **Planning（规划器）：** 提供上面提到的 CoT、ToT 或 ReAct 的代码实现逻辑。

### 🔍 实例解析：Claude Code 里的 Agent 框架

最近非常火的 **Claude Code**（Anthropic 推出的 CLI 开发者 Agent 工具），就是一个极其典型的、面向开发者场景的 **Agent 框架应用**。

在 Claude Code 的世界里，它的 Agent 框架核心逻辑是这样运作的：

- **环境感知（Environment）：** 框架允许 Claude 访问你的终端（Terminal）和 Git 仓库。
- **工具箱（Tools Library）：** 框架给 Claude 注入了极其硬核的专属工具，比如 `view_file`（读文件）、`edit_file`（用类似 patch 的方式精准修改代码）、`grep_search`（全局搜索代码）、`execute_command`（运行测试命令）。
- **极简循环（Loop）：** Claude Code 内部运行着一个紧密的 **思考-行动-观察** 循环。
  > **用户输入：** “帮我修复这个项目的登录 Bug。”
  > **Agent 思考：** 我需要先找到登录相关的代码。
  > **Agent 行动：** 调用 `grep_search` 工具搜索 "login"。
  > **环境反馈：** 返回了三个文件列表。
  > **Agent 思考：** 看起来 `auth.py` 最可疑，我读一下。
  > **Agent 行动：** 调用 `view_file` 读取代码……（循环往复，直到通过 `execute_command` 运行测试成功后，直接作答并收工）。

开源社区里最著名的通用 Agent 框架有 **LangChain、CrewAI、AutoGen、LangGraph** 等。而 Claude Code 则是 Anthropic 官方针对“写代码和项目维护”这一垂直场景，量身定做的一套闭源、高强度优化的专属 Agent 框架。

## 2. 两种 Agent 思考流程 CoT (Chain of Thought) 与 ToT (Tree of Thoughts) 的区别

这两者都是为了解决大模型“直觉作答容易出错”的问题，迫使模型像人类一样**一步一步思考**。但它们的结构和适用场景有很大不同。

### 🔗 CoT (链式思考)：线性的单行道

- **核心逻辑：** 顺藤摸瓜。给模型一个复杂的逻辑题，模型会生成一串形如“因为 A，所以 B；因为 B，所以 C”的线性推理链。
- **特点：** **没有回头路**。如果第一步（A $\rightarrow$ B）算错了，后面的推理就会全盘皆输，但它速度快，消耗 Token 少。
- **适合场景：** 相对确定的数学应用题、简单的常识推理。

### 🌳 ToT (树状思考)：多路径的分叉树

- **核心逻辑：** 广撒网，优中选优。模型在第一步会产生**多个**可能的思考方向（分叉），然后对每个方向进行自我评估（比如打分：好、中、差），砍掉差的，保留好的，再继续往下分叉。
- **特点：** **支持回溯（Backtracking）和全局规划**。如果走着走着发现是一条死路，它可以退回到上一个分叉口，选择另一条路。
- **适合场景：** 极其复杂的动态规划问题（如：数独、24点游戏、复杂的创意写作创意筛选）。

### 📊 对比总结


| 特性       | CoT (链式思考)   | ToT (树状思考)           |
| -------- | ------------ | -------------------- |
| **结构**   | 线性链条（一条路走到黑） | 树状分支（多条路径并行与试错）      |
| **核心机制** | 顺序推理         | 评估、剪枝（放弃错误路径）、回溯     |
| **计算成本** | 低（单次生成）      | 极高（需要多次生成和评估）        |
| **人类类比** | “直觉推理，一气呵成”  | “谋定而后动，举棋不定时多想几种可能性” |

# Agent 引导

要引导 Agent，不能把它当成一个黑盒，而是要像**管理一个新员工**一样：如果他事情办砸了，你要知道他是**听错了需求（Prompt）**、**漏了步骤（Planning）**、**用错了工具（Tools）**，还是**记性不好（Memory）**。

为了让你在它“翻车”时精准喂药，我们需要剖析 Agent 内部最核心的**工程运转机制**。

---

## 🧭 Agent 的黄金内循环：ReAct 机制

目前市面上 90% 的单体 Agent（包括 Claude Code、Artifacts、以及各种开源智能体）底层都在跑一个叫 **ReAct (Reason-Action-Observation)** 的死循环。

当 Agent 达不到要求时，通常是这个循环的某个环节断了。我们来看看它每一步在干嘛，以及怎么介入：

### 1. Thought（思考阶段）

* **内部机制：** 模型在心里默默分析：“用户要我写个爬虫，我需要先看看目标网站的结构。”
* **翻车表现：** * **幻觉：** 瞎编一个不存在的步骤（比如它觉得可以直接用意念读取数据）。
* **死循环：** 卡在同一个思路里出不来，反复想同一件事。


* **如何引导：** * **在 Prompt 中加入约束（Few-Shot）：** 给它一个正确的思考范例。
* **显式打断：** 如果框架支持（如 LangGraph 的 Breakpoint），在 Thought 之后拦截，人工修改它的思考方向。



### 2. Action（行动/选工具阶段）

* **内部机制：** 模型决定：“我要调用 `web_search` 工具，参数是 `特斯拉2026财报`。”
* **翻车表现：**
* **参数错误：** 把 JSON 格式写错，导致工具报错。
* **工具选错：** 该用数据库查询的时候，它跑去用谷歌搜索。


* **如何引导：**
* **严厉的 Schema 限制：** 在代码层使用 Pydantic 强行约束工具的输入格式。
* **精简工具箱：** 不要一股脑给它 20 个工具，不需要的工具不要传给它。包包里工具越多，它越容易拿错。



### 3. Observation（观察/拿结果阶段）

* **内部机制：** 工具执行完毕，返回结果：“找到以下三条新闻...”。
* **翻车表现：**
* **信息过载：** 网页返回了 10 万字，模型直接把垃圾信息也当成了真理，或者超出了上下文长度（Context Window）。
* **误读结果：** 工具明明报错了（如 `404 Not Found`），大模型却以为这是正确的网页内容。


* **如何引导：**
* **数据清洗：** 在工具返回给大模型之前，用 Python 代码把 HTML 里的广告、无关标签删掉，只把纯文本喂回给模型。
* **错误捕获：** 如果工具报错，在代码里把错误信息包装得更人性化：“*工具报错了，请更换关键词重新搜索*”。

## 🛠️ 引导 Agent 做正确的四大“杠杆”

当你的 Agent 达不到预期，你有四个层面的武器去修正它：

```
[用户 Prompt] ──> [Prompt/Few-shot 引导] ──> [状态与记忆干预] ──> [人工人在回路 (HITL)]

```

### 杠杆一：Prompt 维度的“规矩设定”

别只给任务，要给**标准 SOP（标准作业程序）**。

* **反面教材：** “帮我分析这个文件。”
* **正面引导：** “你在分析文件时，必须严格执行以下步骤：1. 先列出文件的核心大纲；2. 针对大纲中的每一项，调用 `search_db` 工具检查是否有背景数据；3. 如果数据缺失，**绝对不允许编造**，直接在报告中注明。”

### 杠杆二：Few-Shot（少样本提示）的“标准答案”

大模型是顶级的模仿者。如果它某一步总是做错，直接在 System Prompt 里塞一个**正确的“思考-行动-观察”的完整历史记录**给它看。它看到有标准前车之鉴，就会依葫芦画瓢。

### 杠杆三：Memory（记忆）的“精准断片”

Agent 的记忆通常是动态追加的。如果它前面犯了个错（比如找错了文件），这个错误记录就会留在它的 Context（上下文）里，导致它后面**步步皆错**。

* **引导技巧（工程层面）：** 引入 **Memory Management（记忆清理）**。如果发现它走错路，在代码里写个逻辑，把过去 3 轮错误的对话历史“擦除”或“压缩”，只留下正确的结论，让它“失忆”后再重新思考。

### 杠杆四：HITL (Human-in-the-Loop, 人人在回路)

这是对抗 Agent 失控的终极武器。像 Claude Code 为什么这么准？因为它在执行高危动作（比如 `rm -rf` 或者修改核心代码）前，会停下来问你：`[y/n]`？

* **引导技巧：** 在你的 Agent 架构中，在 **Action（行动）** 和 **Observation（观察）** 之间加一个闸门。当 Agent 提出一个计划后，系统暂停，把计划推给你的屏幕：
> “系统检测到 Agent 准备调用：`delete_user_data`，是否允许？如果你觉得它想错了，可以在这里输入你的指导意见：___________”
> 你输入：“不对，你应该先去备份，而不是直接删除。”
> 框架把你的这句话作为 Observation 喂回给 Agent，Agent 就会恍然大悟，修正路线。

Agent 开发者和高级用户面临的巨大痛点：**提示词冗余（Prompt Redundancy）** 与 **黑盒迭代（Black-box Evolution）**。

随着 Anthropic、OpenAI 等大厂对 Agent 产品（如 Claude Code、ChatGPT Tools 等）进行高频的底层升级，你作为用户，确实很难看清它们每天都在 System Prompt（系统提示词）里偷偷加了哪些新规矩。

在目前的强 Agent（如 Claude 3.5/4 世代）背景下，**过度重复、臃肿的提示词反而会带来副作用**：

* **注意力分散（Attention Dilution）：** 长文本上下文注意力机制表明，如果你的 User Prompt（用户提示词）里塞满了各种“严禁、必须、绝对不要”，大模型在处理长上下文时，注意力焦点可能会被这些限制性词汇带偏，反而忽略了你真正要它执行的**业务核心逻辑**。
* **过度防御（Over-defensiveness）：** 如果你反复强调“绝不准编造，数据缺失就注明”，而 Agent 底层新版本也强化了这条规则，两层叠加可能会导致 Agent 变得极度“胆小”。它可能稍微遇到一点模糊的数据，就直接罢工说“我查不到，我不编造”，失去了原本合理的推理和联想能力。
* **Token 成本与延迟：** 冗余的废话会无谓地消耗 Token，拉长 Agent 的思考时间。

## 破局之道：如何“感知”并顺应 Agent 的悄悄迭代？

既然看不到源码，我们可以通过**工程化和策略化**的方法，把黑盒变成半透明。

### 🧭 策略一：从“保姆式规定”转向“结构化交付标准”

不要教 Agent 怎么做（因为它的新版本可能已经学过怎么做了），而是**死死卡住输出的格式和标准**。

* **以前的防翻车写法（教做事）：** “如果数据缺失，你千万不要编造，要在报告里写明查不到，听到没有？”（容易与新版本规则冲突）
* **现在的优雅写法（卡标准）：**
> “请严格按照以下 JSON 格式输出报告：
> `{ "指标名称": "...", "数值": "...", "数据置信度": "确切真实 / 缺失留空" }`”

这种写法的好处是：无论 Agent 自身版本怎么迭代，它内部的 SOP 怎么变，你只要求最终产物。如果它新版本变聪明了，它自然能填满这个 JSON；如果数据真的缺失，它也必须按照你给的“缺失留空”标准来交差。

### 🧪 策略二：建立你自己的“测试基准（Benchmark）”

既然官方不给你发 Release Notes（更新日志），你就自己当质检员。

* **操作方法：** 准备一个**你已知有坑、必定会翻车**的测试大任务。比如，故意扔给它一个包含了虚构公司名称、或者故意删掉了某年关键财务数据的文档。
* **定期重测：** 每次你怀疑它升级了，或者每隔两周，把这个“钓鱼任务”原封不动扔给它。
* *上周的表现：* 它瞎编了一个数据（说明老版本有 Bug）。
* *这周的表现：* 它突然很诚实地报错说“未找到XX数据”（说明官方迭代修复了）。


* 一旦发现它不翻车了，你就可以把你在 User Prompt 里临时加的“补丁提示词”删掉，保持提示词的精简和高效。

### 🔄 策略三：利用 Agent 自身的“反思（Reflection）”机制

很多现代 Agent 产品在回答完之后，都具备了审查自身链路的能力。当你发现它今天做得很完美，你想知道是它自己变聪明了，还是纯属运气好，你可以直接追问它：

> 💬 **你可以这样问：**
> “你刚才处理缺失数据的逻辑非常棒。请告诉我，你在刚才的整个执行链条中，具体是在哪一个步骤发现数据缺失的？你当时触发了什么内置规则让你决定不编造，而是直接注明？”

高级 Agent 会诚实地拆解它的思维链（Thought Process），甚至会告诉你：“*在我的基础操作指南中，如果搜索结果为空，我需要优先向用户汇报，而不是进行模糊推理。*” 这样，你就变相地把它的底层更新日志给“套”出来了。

---

与 Agent 共同进化，最核心的心态是：**把高频、细节的控制权交给官方迭代；把结构、标准和边界的控制权留在自己手里。** 你的 Prompt 应该随着它的变聪明而变得越来越精简，直到有一天，你只需要像对一个资深专家一样，说一句话，它就能心领神会。
